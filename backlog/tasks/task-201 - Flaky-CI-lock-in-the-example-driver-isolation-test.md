## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Observed twice within an hour (PR #195 on 3.13, PR #196 on 3.11, 2026-09-30): tests/test_example_driver_isolation.py around line 548 intermittently fails on hosted CI runners with DRIVER-ERROR: unhandled OperationalError: database is locked, from conn.execute("PRAGMA wal_checkpoint(TRUNCATE)") in the run_repro driver. The rerun goes green both times. Both failing PRs were comments/test-only diffs, so it is unrelated to any recent change. The lock is between the driver's checkpoint and whatever else holds the database; worth either a busy_timeout/retry around the checkpoint or a serialization of the driver's connections, whichever matches the test's intent.

DIAGNOSIS LANDED 2026-11-09 (set 79, candidate e4992fc on b85316e, the schema-warm-up fix): the mechanism behind all nine occurrences is closed and EMPIRICALLY PROVEN by the independent skeptic, which compiled the official 3.46.1 amalgamation and reproduced it deterministically. Chain, every link source-cited and reproduced: wal_checkpoint carries PragFlg_NeedSchema (pragma.h:648), so a fresh connection's PREPARE of the pragma loads the schema under a read transaction (pragma.c NeedSchema gate precedes mode parsing and opcode emission); a read transaction reaching walTryBeginRead while the WAL_RECOVER_LOCK is held by another process returns SQLITE_BUSY_RECOVERY (wal.c:3083); the btree read-begin retries 261 through the connection busy timeout (btree.c:3694-3695) and then the code escapes the prepare retry loop (prepare.c:863-871 retries only ERROR_RETRY/SCHEMA), the API boundary strips it to BUSY (apiHandleError errMask 0xff, and CPython 3.11-3.14 never enable extended codes), and Python raises OperationalError('database is locked') at the execute, before OP_Checkpoint's exact-equality busy-to-row conversion exists (vdbe.c:7839). Mode-independent by structure: identical instant raises reproduced for PASSIVE/TRUNCATE/RESTART. With the schema warm, the pragma program contains NO OP_Transaction (EXPLAIN: Init, Expire, Checkpoint, ResultRow, Halt) and the same staged contention converts to the busy=1 result row; SETLK_TIMEOUT is off in every build the runners use (checked CPython PCbuild, Mac build-installer, Ubuntu packaging), so TIMEOUT codes cannot occur. TWO CORRECTIONS to the occurrence-9 note's wording, folded into the code comment before landing: the busy handler IS consulted for 261 at the btree level (the failure is the full 10s wait THEN the raise, measured 10.014s, not an instant refusal; 'timeout cannot help' was wrong), and therefore each occurrence implies the wal-index locks were held or renewed for OVER TEN SECONDS, longer than an ordinary recovery of this WAL takes. THE TRIGGER REMAINS AN OPEN INFERENCE: no process is named that holds those locks that long (a SIGSTOPped process never releasing its locks is the natural suspect this driver itself creates; the skeptic's doubt: if the real CI trigger is something the staging does not model, the warm-up may relocate the flake rather than kill it).
