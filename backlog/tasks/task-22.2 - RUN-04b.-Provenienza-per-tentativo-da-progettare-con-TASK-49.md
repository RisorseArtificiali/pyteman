A synchronous mkdir failure (e.g. token collision) finalizes that same row to 'failed' immediately; a killed process leaves the row at 'running' forever, by design, and nothing in the module ever reinterprets that. Round 3 (2026-09-18, high-effort code-review gate on the final 4-file diff, per the project's enforced completion gates): three Important findings and two Notes, all applied directly, none deferred. (1) The PK check used PRAGMA table_info's `pk` column (a column's 1-based position within the primary key, not a yes/no flag) as `row[5] == 1`, so a foreign table with `PRIMARY KEY(attempt_id, experiment)` passed preflight since attempt_id is still first in that composite key; sqlite's real uniqueness constraint is scoped to the pair, so a genuine duplicate attempt_id could insert silently under a different experiment. The reviewer confirmed this live: two rows sharing one attempt_id, run_matrix returning 'done' with no error. Fixed by requiring attempt_id be the *sole* column in the primary key (`pk_members != [(1, "attempt_id")]`); new regression test test_a_composite_primary_key_sharing_attempt_id_is_also_refused, confirmed red (DID NOT RAISE) against the unfixed check and green after restoring it. (2) The attempts-shape checks ran after `_migrate_v1_to_v2` and after all three CREATE TABLE IF NOT EXISTS statements, both of which autocommit or write rows a later rollback cannot undo, so the refusal's own "Nothing has been changed" message was false: the reviewer's probes showed a fresh db gained schema_meta/results_superseded/attempts before refusing, and a v1 db was fully migrated to v2 shape before refusing. Fixed by moving the attempts-shape check (both the column-set check and the PK check) to run before any of that DDL or migration inside _ensure_schema; the two existing tests' "nothing changed" assertions, which queried schema_meta (no longer created before the refusal), were rewritten to assert `SELECT name FROM sqlite_master WHERE type='table'` returns only `('attempts',)`, a strictly stronger check. (3) The finish-transaction's `UPDATE attempts SET status=... WHERE attempt_id=?` did not check its rowcount, so a concurrently deleted attempts row let the UPDATE silently match zero rows while the results write still committed as 'done', an attempt with no corresponding attempts-table row. Fixed by mirroring `_adopt_stored_rows`'s existing rowcount-guard pattern (`cur.rowcount != 1` -> rollback -> raise MatrixStorageError); new regression test test_a_concurrently_deleted_attempts_row_stops_the_finish_write (tests/test_matrix_attempts.py), confirmed red (DID NOT RAISE) against the unfixed UPDATE and green after restoring it. Note (a): the comment above the old check ordering claimed a rationale ("once schema_meta says v3, every future call trusts that") that the reordering fix made moot; rewritten to state the actual reason (DDL autocommits, so the check must run first). Note (b): README.md's attempt-lifecycle claim ("before anything touches the filesystem") overstated the guarantee, since the lock file, artifact root, experiment directory and results db may already exist from earlier calls; reworded to scope the claim to "anything *it* does to the filesystem" (this attempt's own directory specifically).
